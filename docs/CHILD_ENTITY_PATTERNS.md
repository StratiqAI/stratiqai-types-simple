# Best Practices: Child Entity Access Patterns

## Overview

For child entities like `DocLink` that have a `parentId` referring to a parent `Project`, there are specific patterns for:
1. **GraphQL Operation Design** - How to reference the child entity
2. **DynamoDB Key Structure** - How to build keys for efficient lookups
3. **Security** - Preventing IDOR (Insecure Direct Object Reference) attacks

## Key Input Types

Your schema defines three key input types:

```graphql
# For root/parent entities (Project, Workflow, etc.)
input PrimaryKeyInput {
  id: ID!
}

# For listing child entities (requires parent context)
input ParentKeyInput {
  parentId: ID!
}

# For single child entity operations (prevents IDOR)
input CompositeKeyInput {
  id: ID!
  parentId: ID!
}
```

## GraphQL Operation Patterns

### 1. **Get Single Child Entity** (Use `CompositeKeyInput`)

**Why:** Requires both `id` and `parentId` to prevent IDOR attacks. Even if someone knows a DocLink ID, they can't access it without the correct parentId.

```graphql
query GetDocLink($key: CompositeKeyInput!) {
  getDocLink(key: $key) {
    id
    parentId
    filename
    status
    # ... other fields
  }
}
```

**Usage:**
```typescript
const result = await client.query({
  query: Q_GET_DOCLINK,
  variables: {
    key: {
      id: "doclink-123",
      parentId: "project-456"  // Must match the actual parent
    }
  }
});
```

### 2. **List Child Entities** (Use `ParentKeyInput`)

**Why:** Lists all children of a specific parent. Only requires `parentId` since you're querying by parent.

```graphql
query ListDocLinks(
  $key: ParentKeyInput!
  $limit: Int
  $nextToken: String
) {
  listDocLinks(key: $key, limit: $limit, nextToken: $nextToken) {
    items {
      id
      parentId
      filename
      # ... other fields
    }
    nextToken
  }
}
```

**Usage:**
```typescript
const result = await client.query({
  query: Q_LIST_DOCLINKS,
  variables: {
    key: {
      parentId: "project-456"  // List all DocLinks for this project
    },
    limit: 20
  }
});
```

### 3. **Create Child Entity** (Use `ParentKeyInput`)

**Why:** When creating, you only need the parent context. The child `id` is generated by the backend.

```graphql
mutation CreateDocLink(
  $parentKey: ParentKeyInput!
  $input: CreateDocLinkInput!
) {
  createDocLink(parentKey: $parentKey, input: $input) {
    docLink {
      id
      parentId
      # ... other fields
    }
    userErrors {
      message
      code
      field
    }
  }
}
```

**Usage:**
```typescript
const result = await client.mutate({
  mutation: M_CREATE_DOCLINK,
  variables: {
    parentKey: {
      parentId: "project-456"
    },
    input: {
      filename: "document.pdf",
      documentId: "doc-123",
      status: notUploaded
    }
  }
});
```

### 4. **Update/Delete Child Entity** (Use `CompositeKeyInput`)

**Why:** Same security principle as Get - requires both `id` and `parentId` to prevent unauthorized access.

```graphql
mutation UpdateDocLink(
  $key: CompositeKeyInput!
  $input: UpdateDocLinkInput!
) {
  updateDocLink(key: $key, input: $input) {
    docLink {
      id
      # ... updated fields
    }
    userErrors {
      message
      code
      field
    }
  }
}
```

**Usage:**
```typescript
const result = await client.mutate({
  mutation: M_UPDATE_DOCLINK,
  variables: {
    key: {
      id: "doclink-123",
      parentId: "project-456"  // Backend validates this matches
    },
    input: {
      filename: "updated-name.pdf"
    }
  }
});
```

## DynamoDB Key Structure

### Recommended Pattern: Composite Key with Parent Context

For child entities, use a composite key structure that includes parent context:

```
Partition Key (PK): USER#<ownerId> or TENANT#<tenantId>
Sort Key (SK): PROJECT#<parentId>#DOCLINK#<id>
```

**Why this structure:**
1. **Security**: All items are scoped by owner/tenant in the partition key
2. **Efficiency**: Can query all DocLinks for a project using `PK = USER#<ownerId>` and `SK begins_with PROJECT#<parentId>#DOCLINK#`
3. **Direct Access**: Can get a specific DocLink using full PK/SK
4. **Parent Validation**: The parentId in the SK allows backend to validate parent ownership

### Alternative: GSI for Parent-Child Queries

If you need to query by parent more efficiently, use a GSI:

```
GSI1PK: PROJECT#<parentId>
GSI1SK: DOCLINK#<id>
```

This allows:
- Query all DocLinks for a project: `GSI1PK = PROJECT#<parentId>` and `GSI1SK begins_with DOCLINK#`
- Get specific DocLink: `GSI1PK = PROJECT#<parentId>` and `GSI1SK = DOCLINK#<id>`

## Security Best Practices

### 1. **Always Validate Parent Ownership**

In your resolver, validate that:
- The `parentId` in the key matches the actual parent of the child entity
- The user has access to the parent entity
- The parent exists and is not deleted

```typescript
// Pseudo-code for resolver validation
async function getDocLink(key: CompositeKeyInput, user: User) {
  // 1. Get the DocLink
  const docLink = await dynamodb.getItem({
    PK: `USER#${user.id}`,
    SK: `PROJECT#${key.parentId}#DOCLINK#${key.id}`
  });
  
  // 2. Validate parentId matches
  if (docLink.parentId !== key.parentId) {
    throw new Error("Parent ID mismatch");
  }
  
  // 3. Validate user has access to parent
  const parent = await getProject({ id: key.parentId });
  if (!canAccess(parent, user)) {
    throw new Error("Unauthorized");
  }
  
  return docLink;
}
```

### 2. **Use Composite Keys to Prevent IDOR**

By requiring both `id` and `parentId`, you prevent:
- Accessing a DocLink by guessing its ID
- Accessing a DocLink from a different parent
- Bypassing parent-level permissions

### 3. **Validate Parent Context in Mutations**

When creating/updating, always validate:
- The parent exists
- The user has permission to modify the parent
- The parentId in the key matches the entity's actual parentId

## Example: Complete Flow

### Scenario: Get a DocLink for a Project

```typescript
// 1. Client knows the project ID and docLink ID
const projectId = "project-456";
const docLinkId = "doclink-123";

// 2. Client constructs CompositeKeyInput
const key = {
  id: docLinkId,
  parentId: projectId
};

// 3. GraphQL query
const result = await client.query({
  query: Q_GET_DOCLINK,
  variables: { key }
});

// 4. Backend resolver:
//    - Validates parentId matches docLink.parentId
//    - Validates user has access to the project
//    - Returns docLink if authorized
```

### Scenario: List All DocLinks for a Project

```typescript
// 1. Client knows the project ID
const projectId = "project-456";

// 2. Client constructs ParentKeyInput
const key = {
  parentId: projectId
};

// 3. GraphQL query
const result = await client.query({
  query: Q_LIST_DOCLINKS,
  variables: { 
    key,
    limit: 20 
  }
});

// 4. Backend resolver:
//    - Queries DynamoDB: PK = USER#<userId>, SK begins_with PROJECT#<parentId>#DOCLINK#
//    - Validates user has access to the project
//    - Returns paginated list of DocLinks
```

## Summary

| Operation | Input Type | DynamoDB Pattern | Security |
|-----------|-----------|------------------|----------|
| Get child | `CompositeKeyInput` | GetItem with full PK/SK | Validates parentId match |
| List children | `ParentKeyInput` | Query with parent prefix | Validates parent access |
| Create child | `ParentKeyInput` | PutItem with generated id | Validates parent exists & accessible |
| Update child | `CompositeKeyInput` | UpdateItem with full PK/SK | Validates parentId match |
| Delete child | `CompositeKeyInput` | DeleteItem with full PK/SK | Validates parentId match |

## Key Takeaways

1. **Use `CompositeKeyInput`** for single child operations (get, update, delete) - prevents IDOR
2. **Use `ParentKeyInput`** for list/create operations - provides parent context
3. **Always validate parent ownership** in resolvers - don't trust client input
4. **Structure DynamoDB keys** to include parent context in the sort key
5. **Use GSI** if you need efficient parent-child queries
6. **Validate parent access** before allowing child operations
